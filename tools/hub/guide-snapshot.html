Bramblewood Arena — Standard of Creation

This is the "start here" doc: a distilled summary of game-design.md (the full history) plus the working rule that governs every doc in this family, including this one.

The rule

Before starting ANY new work, read style-guideline.md and mechanics-guideline.md first. These two are the mandatory, cross-cutting checklists — visual/UX/motion/sound/copy conventions in one, game-design/engine conventions in the other — that keep every new addition consistent with everything already shipped, whether or not you already know which specific system you're about to touch. They're short and meant to be read every time, not once.

Then, before doing any work on a specific concept — audio, combat, economy, VFX/animation, UI/layout, or the build pipeline — read that concept's context doc too (listed below). Each one holds the accumulated decisions, gotchas, and current shape of that system; skipping it risks silently redoing a decision that was already made, or breaking a constraint that isn't obvious from the code alone (a timing dependency, a deliberately-rejected alternative, a reason a value is what it is). The guideline docs are the fast top-level pass; the context docs are where the implementation-level detail lives.

After finishing a piece of work that touches one of these concepts, update its context doc — not by appending a changelog entry, but by editing the relevant section in place so the doc always describes the CURRENT system, the way this doc and game-design.md already do. If the work also establishes or changes a cross-cutting convention (a new card-anatomy rule, a new status- effect shape, a new testing requirement), fold that into style-guideline.md/ mechanics-guideline.md the same way — in place, not as a changelog. A context or guideline doc that just accumulates history without editing existing sections stops being useful as a reference; the version-addenda (game-design-vNN-addendum.md) are where the changelog/history belongs, not these.

This doc itself gets the same treatment: when the game's overall shape changes enough that this summary goes stale, edit it in place rather than leaving it to drift.

Mandatory pre-work checklists

  • style-guideline.md — design tokens, card anatomy (CSRE), motion conventions, sound conventions, copy/naming conventions, layout/responsiveness, theming. Read before any visual or UX-facing change.

  • mechanics-guideline.md — the resource model, skill/passive architecture, status-effect shapes, trigger/action vocabulary, combat/column semantics, card data/leveling, and the decision-discipline process (when to ask instead of guessing). Read before any new card effect, status, resource, trigger, action, or combat-rule change.

Context docs (read the relevant one before working on that concept)

  • context-audio.md — SoundKit, the settings-menu volume sliders (Music/SFX/Voice), and the speech/dialogue framework's voice cues. Read before touching any sound, any volume control, or the speech bubble system.

  • context-combat-engine.md — the board model (center-slot + flanks), turn order, targeting rules, and the engine's trigger/effect vocabulary. Read before touching combat resolution, card effects, or anything in bramblewood-engine.js.

  • context-economy-progression.md — the three currencies (Gold/Prayer/Devilry in-match, Gold/Gems/Magic Dust out-of-match), card leveling, and the Forge. Read before touching costs, rewards, or progression.

  • context-vfx-animation.md — the GSAP entrance/Flip system, pendingEntranceOrigins, particle/celebration utilities (star-fall, emoji-burst, card-flip), and speech bubbles' visual half. Read before adding or changing any animation.

  • context-ui-layout.md — the card-sizing CSS variables, the topbar/content-width split, responsive breakpoints, and general layout conventions. Read before touching CSS structure.

  • context-architecture-pipeline.md — file layout, the assembly script, canonical data files, the test suite, and publishing. Read before rebuilding, adding a new source file, or setting up a fresh working directory.

Current state (as of Version 30 / 2026-09-18)

Bramblewood Arena is a single-file HTML5 card game, assembled from arena_template.html (CSS + skeleton) + arena_app.js (all application logic) + bramblewood-engine.js (DOM-free combat) + canonical/cards.json + canonical/characters.json, stitched by assemble_arena.py into bramblewood-arena.html, then published as a claude.ai Artifact (https://claude.ai/code/artifact/51c1f54c-536f-4e69-b99d-2bd2c523f7a1).

Core loop: pick a Bramble (HQ passive) and a Leader, build a 20-card deck from your unlocked cards, fight either the local AI, another human on the same device (PC mode), or work through the Conquest campaign / Raid boss tab. Combat resolves a full round at once inside the engine, then replays as a paced sequence of animated events on the client.

Board: each side has {left:[], center:[], right:[]}; center holds exactly one card and is where the first card played always lands. Turn order interleaves left-to-right by column across both sides (not "resolve my whole row, then yours"). See context-combat-engine.md for the full targeting/turn-order rules.

Progression: three out-of-match currencies (Gold/Gems/Magic Dust) power a 0→10 card-leveling system via the Forge tab. See context-economy-progression.md.

Roster: 221+ cards across 52+ archetypes, defined in canonical/cards.json, editable live through the Codex's card editor (baseline + a live-db overlay).

Testing: a Playwright regression suite (74+ files as of this writeup, test_*.js) covers engine correctness and UI/animation behavior. Run individually or in small parallel batches (4-8) — see context-architecture-pipeline.md for why running all of them in one large parallel batch produces transient, CPU-contention-driven failures that are not real regressions.

Full history: game-design.md remains the complete, chronological record of every version — this doc summarizes it, it doesn't replace it. The game-design-vNN-addendum.md files are the per-session changelogs; game-design-action-items.md and roadmap-and-backlog.md are the living backlog/roadmap; style-guideline.md and mechanics-guideline.md are the mandatory cross-cutting checklists introduced 2026-09-21.

Bramblewood Arena — Style Guide (mandatory before shipping any visual/UX change)

How this doc is used

Read this before writing or reviewing ANY change that touches how the game looks, sounds, moves, or reads — a new card visual, a new UI panel, a new animation, a new sound cue, new copy in a button or dropdown. It is a checklist, not background reading: if a planned change would violate a rule below, either fix the plan so it doesn't, or flag it to the user as a decision item exactly the way game-design-action-items.md already flags ambiguous asks — don't silently ship a violation and don't silently "improve" the rule on your own judgment mid-task.

This doc holds the CROSS-CUTTING conventions — the ones that apply no matter which subsystem you're touching. The context-*.md docs remain the per-system deep reference (exact CSS variable names, exact function names, the full history of why a value is what it is) — read the relevant one too before touching that system. This doc is the fast top-level pass; the context docs are where the details live. When the two ever seem to disagree, the context doc is more likely current (it's the one this doc's own process below tells you to update after a change) — fix this doc to match rather than assuming the context doc is stale.

1. Design tokens — never hand-write a color

Every color is a CSS custom property, defined once on the bare :root (light theme) and redefined under @media (prefers-color-scheme: dark) guarded by :root:not([data-theme="light"]) plus again under :root[data-theme="dark"] for the explicit toggle. A new UI element takes its color from --bg/--surface/--surface-2/--surface-3/--surface-border/--ink/ --ink-muted/--ink-soft/--accent/--accent-strong/--accent-ink/--attack/--health, never a literal hex value — a literal that "looks right" in whichever theme you happened to preview breaks silently in the other one. --page-wood/--page-ink are the ONE deliberate exception: they exist specifically for content sitting directly on the outer wood background rather than inside a --surface panel (the topbar's Home/Settings/Back buttons, the home menu's ghost buttons) — --page-ink is fixed-light in both themes on purpose, because --ink flips per theme and a --surface-paired ink color goes unreadable on the always-dark wood backdrop. Don't reuse --page-ink for anything that DOES sit inside a --surface panel, and don't give --ink a --page-wood-specific override — that was a real, already-fixed contrast bug (game-design-action-items.md, batch #3, item 1); the fix was a new token, not patching the old one.

Three type families, each with a job — don't introduce a fourth without a real reason: Nunito (body text, buttons), Baloo 2 (headings, card names/stats, UI labels — the game's primary "voice"), MedievalSharp (the brand wordmark only, for the chivalric flavor — not for general UI text, it doesn't hold up at small sizes or in long strings).

2. Card anatomy (CSRE — Card Surface Real Estate)

cardTileHTML() is the one renderer for every card EXCEPT the live battlefield (boardCardHTML() is separate, on purpose — combat has its own animation needs that would fight anything below). Current anatomy, top to bottom, and why:

  • Top band, shared, top:-7px: cost badge (far left), skill/ability badges (center), Wait badge (far right). These three were deliberately unified onto one shared band — keep new top-of-card indicators on this same band rather than inventing a new absolute position, and don't move skill badges to a different vertical position than cost/wait again (they were once moved to top:16px to avoid crowding cost, which instead put them on top of the card name — a real, already-fixed bug; see game-design-action-items.md's "Card visual design" category).

  • Zero-cost / zero-wait hiding rule (CSRE): a $0 cost or $0 Wait badge renders as NOTHING, not a bare "🪙0" or "⏱0" chip — apply this through the shared costBadgeParts() helper, not a one-off check, so hand cards/deck tiles/the Leader widget/the hover popover all stay consistent.

  • Name, below the top band, centered, Baloo 2 700, currently 13px/1.12 line-height — sized to read clearly at the in-match card size; if you change in-match card size, re-check this against a card with the longest real name in the roster, not a short placeholder.

  • Stats (⚔/❤), bottom of the tile via margin-top:auto in flex-column contexts (board/hand/ leader) — the pool/Codex/deck-picker grid is NOT flex-column (display:block), so stats sit in normal flow there instead; don't assume one universal position without checking which context you're in first (this was a real, confirmed-wrong assumption once — verify with a real getComputedStyle check, don't infer from a CSS comment written for a different context).

  • .rarity-band: a bottom-anchored gradient scrim, both a rarity-color indicator and text legibility backing. Current tuning: 50% of tile height, capped at .58 max black alpha, with a transparent 0%, transparent 30% lead-in. If retuned, re-check specifically against Common (#ffffff-family) and Starter rarity colors — a too-dark scrim flattens those two into an indistinguishable grey wash before it visibly hurts any other, more-saturated rarity.

  • Pitch/discard-resource badge, bottom edge, dormant by default: shows nothing for the universal 1-Lumber baseline, and only appears once a card's real discard yield deviates from that baseline (a non-1 Lumber amount — including 0, flagged as abnormal — or any other resource above 0). Don't make this always-visible; that was explicitly rejected as noise.

  • Hover flourish (.card-tile-magnetic): cursor-following 3D tilt (--ctTiltX/--ctTiltY, up to ~7-10°, eased back to flat on mouseleave via CSS transition, no JS needed for the reset) plus a diagonal shimmer sweep reusing the card's existing ::after glass-shine layer. Opt a NEW context into this class only if it's a browsing/picking context (deck pool, castle/Bramble picker, Codex) — never the hand strip, the leader widget, or anything board-related, which already carry their own combat/selection-specific animation this would fight.

  • Foil/splashEffect is independent of rarity — a card can be Rare AND Foil. Never route a print-variant effect through the rarity field again (that was the original bug this field split fixed).

  • Castle/HQ tiles render through this SAME cardTileHTML(), with opts.isCastle suppressing cost/wait/attack — don't build a separate castle-specific tile template; "the castle should look like a proper card" was resolved by fixing shared anatomy, not by special-casing castles.

  • A card that is actually yours in the current match (e.g. the tutorial's leader) is rendered with opts.inPlay so it never gets the greyed-out "locked" treatment, even if its data is locked for deck-building.

3. Motion conventions

The GSAP entrance/Flip system (full detail in context-vfx-animation.md) is explicitly "extremely carefully tuned... with many bugfix comments warning against structural changes" — treat that warning as real. Prefer additive changes (a new event branch in renderVfxForEvent, a new pendingEntranceOrigins producer) over restructuring the dispatch or the Flip/new-card split. Two rules worth restating because they've each caused a real bug once: new cards must stay explicitly excluded from what Flip.from() targets (it will silently re-diff against stale DOM otherwise), and a played card's hand-uid is not always its board-uid — read the real board uid from the 'play' event, not the uid a card was played with.

A newly-created or newly-repositioned card should reflow LIVE, mid-round, not deferred to round-end. This has been the standing rule since the V21 live-collapse work: death, collapse-in, onAttackedSpawn, and onDeathSpawn tokens all splice into the replay the instant their engine event replays, using matchState.replayRows/replayCards as the live snapshot. A new spawn/ reposition event type should follow this same pattern rather than only showing its final state once the whole round's log finishes.

Interactive-element motion responds to real interaction, not a permanent scripted loop. The magnetic-tilt/shimmer pattern above, and the home-menu buttons' tilt+glow+squash-and-stretch click pop, both replaced an earlier always-rocking scripted keyframe specifically because a cursor-follow/click-triggered treatment reads as alive and a looping idle animation reads as scripted. New interactive chrome (a button, a clickable icon) should follow the interaction-driven pattern, not add a new permanent idle loop. Decorative, non-interactive ambiance (the Autumn Village leaf system) is the deliberate exception — it's atmosphere, not a control, and is allowed to run on its own schedule. The battle board's idle breathing and low-HP tremble (2026-10-06) fall under that exception: they are tiny, ambient, use the CSS translate property so they never fight GSAP's transform tweens, and stop for stunned, frozen and sleeping units. A hover sheen sweeps all the way across its button and exits the far edge — it never parks mid-button.

Squash-and-stretch on click uses asymmetric scaleX/scaleY (not a uniform scale), a bouncy overshoot easing (cubic-bezier(.5,1.75,.75,1.25)), and must respect whatever cursor-tilt custom property is already active so a click mid-hover doesn't snap flat first — copy this shape for any new "big satisfying click" moment rather than a plain scale-pulse.

Anything floating that's anchored to a card (speech bubbles, damage numbers) must follow that card when the page scrolls or the board re-renders — re-anchor every frame, don't position once.

4. Skill VFX (bubbly, obvious, clear — and queued, not simultaneous)

A skill/status animation should read instantly as "something happened" — never as ambiguous noise, and never as one mechanic possibly being confused for another. Three requirements, all non-negotiable for any new skill/status VFX:

  • Bubbly. Favor a playful, physical read over a flat number appearing out of nowhere — a bounce, a shake, a pop, a color pulse. floatText() + shakeEl() + a dedicated SoundKit cue together is the baseline treatment for a new mechanic, not an optional extra.

  • Obvious. A player should never need to read the battle log to know something just happened — the VFX alone announces it.

  • Distinct per mechanic. A new skill/status must be visually AND audibly distinguishable from every mechanic already covered in renderVfxForEvent()/SoundKit (section 3/5 above) — a shared glyph or tone across two different mechanics reads as "the same thing happening twice." This has caused real, since-fixed confusion before: Poison APPLYING a fresh stack and Poison TICKING an existing stack once looked "almost alike" until deliberately given distinct floats (a small "+3☠" for applying vs. a bolder "🫧 5!" for ticking) — see the poisonTick handler's own comment in arena_app.js for the full story. Treat that as the standard of distinctness to match, not the exception.

Skill/status VFX queue — they never play simultaneously or overlap. This is enforced centrally in delayForEvent()/vfxKindOf() (arena_app.js), not left to each effect to self-pace: every event in a round's replay (one per card, per tick, per triggered effect) plays to completion, then the replay waits a breath, then the next one starts. The breath length depends on whether two consecutive events are the same KIND of thing or a different one:

  • Same kind back-to-back → a short, bubbly 200ms breath. Example: two Poison ticks landing in the same round (two different poisoned cards) each get their own SoundKit.bubble() cue and their own damage number, one after another, only 200ms apart — close enough to read as "the same kind of thing, happening again," cute rather than sluggish.

  • A different kind immediately after → a longer 500ms breath. Example: a Poison tick followed by a Bleed tick, or a Freeze status landing right after a Poison tick, gets 500ms — long enough that the switch clearly reads as "a new, distinct thing is happening now," not a blur of the previous effect.

  • "Kind" is ev.type for most events. The one exception is statusFx, which bundles many visually/audibly distinct sub-mechanics (poison/freeze/stun/scar/blind/...) under one event type — there, vfxKindOf() folds in ev.kind too (statusFx:freeze vs. statusFx:poison count as two different kinds, never lumped together as one "statusFx" kind).

  • This rule governs skill/status VFX specifically. Ordinary attacks (hit/hitHQ/evaded), deaths, and Render keep their own separately-tuned pacing (900/1260ms, 550ms, 780ms respectively) — they're already distinct, deliberate beats in the combat rhythm, not part of this same-kind/different-kind skill-effect queue.

  • A brand-new event type needs no new plumbing to join this queue — vfxKindOf()'s default (ev.type) covers it automatically. The only thing a new mechanic must get right is giving a statusFx-shaped event its own distinct ev.kind string, matching no other status's.

5. Sound conventions

Every cue is a SoundKit method built only from the two primitives, tone()/noise() — never call the Web Audio API directly from anywhere else, since volume gating (three independent sliders: SFX/Voice/Music — see context-audio.md) only happens at that one choke point. A new mechanic gets its own NAMED cue distinct from every existing one — this has been the rule since 2026-09-13 ("make sure to add sfx and vfx for all the skills too") and every skill/status shipped since has followed it; don't reuse an existing tone for a new mechanic just because it's "close enough," and don't add a mechanic with no sound at all. SoundKit.stopAll() already cuts every in-flight cue at round end — a new cue with a long tail doesn't need its own cleanup, it inherits this for free as long as it's scheduled through tone()/noise().

6. Copy & naming

Skill/passive names are simple — one or two words ("Hide", "Lunge", "Chained", "Swift"), not a name that crams its parameters into the label ("Freeze (Chance% / Duration)" was cleaned up specifically for this reason). Full mechanical detail belongs in the skill's desc() function and the Codex Reference tab, generated from the same registry — never hand-write Reference tab content that could drift from the registry.

Chance-based mechanics use halves only (1 in 2) — no 1/3s, 1/4s etc. Several independent halves may stack (Swift + Flying + Evade = 7/8 dodge), but each individual roll is a coin flip.

Dropdowns are alphabetical by display label, with two standing exceptions: placeholder/sentinel options ("All types", "— pick a card —", "None") stay first rather than being folded into alphabetical order, and Rarity is never alphabetized (RARITY_DEFS is a meaningful power-tier ladder — alphabetizing would scramble it). Follow both exceptions for any new dropdown rather than re-deriving the question each time.

Be honest about platform limitations rather than faking a feature. The Google SSO investigation is the standing precedent: rather than build a "Sign in with Google" button that couldn't actually authenticate anyone, the honest boundary was explained to the user and a real, smaller feature (the platform's own user capability) was built and clearly labeled for what it actually does. Never ship a control that looks functional but silently does nothing or lies about what happened — the Language button's "Soon"-tagged, genuinely-disabled other languages follow this same precedent.

Think contextually: let a control's surroundings carry its meaning. A label only needs to say what its position doesn't already say. A Show/Hide toggle sitting beside a deck list is obviously about that deck, so it reads "👁 Show" / "🙈 Hide", not "Show deck" / "Hide deck"; a "+1 🪵" next to the card you're holding needn't also be pinned above the Graveyard. Before adding words, ask what the player already knows from where they are looking. Keep the full meaning in the aria-label for screen readers, since they don't get the visual context. (Added 2026-10-06, per explicit request: "always think contextually".)

7. Layout & responsiveness

--match-card-w/--match-card-h is the ONLY sizing lever for in-match cards (.hq-tile, .board-card, .hand-strip .card-tile all consume it identically) — never reintroduce a per-context hardcoded size for these three; that was a real bug (three independently-drifted sizes) before this convention existed. The Codex/pool/deck-editor/Forge's own .card-tile default sizing is a deliberately SEPARATE system (browsing many cards vs. cards actually in play) — don't try to unify the two.

Tiles in the same row (e.g. the Home menu's Settings/Profile/Ranking/Guild/Admin row) are the same width AND height — a wrapper element must not leave its button shrink-wrapped.

One mobile breakpoint handles phone width — add a new responsive rule inside that existing @media block rather than introducing a second breakpoint. .topbar-wrap must never change width based on the current tab; only .content-wrap toggles between the narrow (1220px-capped) and wide (min(1900px, 98-99vw), in-match/map views) layouts — a nav bar that visibly resizes between tabs was explicitly flagged as disorienting and fixed.

When testing any layout change with Playwright, set an explicit viewport ({width:1400,height:1000} has been the working size) rather than trusting the default 1280×720 — a real bug shipped once where hover/mouse-position checks silently no-op'd because the target element rendered below the default viewport's bottom edge, with no thrown error to flag it.

8. Theming

The game already supports light and dark themes via the token system in section 1 — a new component must render correctly in both, not just whichever theme you happened to preview in. Never give a token its only definition inside a prefers-color-scheme/[data-theme] block; the bare :root block is always the light-theme source of truth, with the dark blocks only ever redefining tokens that already exist there. Text placed over the splash art or another dark image must use a light, shadowed color — never the theme --ink, which can be dark.

9. Card art direction (PixelLab) — added 2026-10-02

Every card portrait is pixel art in a Pokémon-like creature style. Three rules apply to all of them, then a "genre" decides the mood.

Always

  • Natural animal anatomy. Not anthropomorphic: no hands, no standing upright like a person, no human clothing by default. Animals without legs (fish, snakes, worms, whales) never get legs; birds perch or fly; quadrupeds stay on four legs.

  • Gear fits the animal's body. "Knight"/"armoured" cards wear armour shaped to the creature (a helmet and back-plate on a dolphin, a gold chest plate on a bee) — never a human suit of armour, never a weapon held in hands. A weapon, if any, is strapped on.

  • Clothing only when it IS the card's identity — e.g. the Cobalt Talon Skirmisher's tiny cloth scarf and padded vest, the Raccoon Nightcrew's thief mask. Keep it small.

Make every card unique — four levers

Two cards from the same faction/species must differ on at least two of these:

  1. Pose — perching, diving, weaving, sprinting, rearing, sleeping, mid-leap, seen from below…
  2. Equipment — none, a bundle, a scroll, a cloth scarf, fitted armour, a shell…

  3. Scene — what the card is DOING, taken from its name/flavor (building a nest, delivering a message, guarding eggs, slipping out of a window with loot).

  4. Background — canyon at sunset, misty canopy, moonlit wall, reef, snowdrift, storm.

A good test: each portrait should tell a different story beat, the way the Wandering Traveller variations read as "generic", "exploring" and "hopeful about the road ahead". If a new portrait could be swapped with a sibling card's without anyone noticing, regenerate it.

Genres (mood by power)

Genre Used for Look
Cute Starter/common and weak cards (low attack + health) Big sparkling eyes, round chubby shapes, bright cheerful palette, everyday scenes
Brave Mid-strength fighters and veterans Confident determined eyes, sturdy shapes, warm rich palette, dynamic action pose
Menacing The strongest creatures, bosses, apex predators (high rarity or very high stats) Narrowed glowing eyes, angular silhouette, dramatic low-angle lighting, darker saturated palette, imposing pose, scars

Rule of thumb when rarity doesn't settle it: attack + health under ~15 → Cute, ~15–27 → Brave, 28+ → Menacing. Faction lines escalate inside one species — e.g. Hummingbird recruits and couriers are Cute, the Dominion Nestguard and Sunspire Envoy are Menacing.

Prompt template

<genre prefix> + natural animal anatomy, not anthropomorphic, no hands, never standing upright like a human, + <subject + pose>, <equipment>, <scene>, <background>. Genre prefixes and the generation/download technique live in pixellab-art-batch-status.md. Generate at 128×128 (Pro returns four variations) with background removal OFF, pick the variation with the clearest silhouette and the most distinct story beat, and crop it with art_staging/crop.py.

Before you ship a visual/UX change, verify:

  1. Every new color is a token, defined in all three required places (bare :root, the prefers-color-scheme dark override, the [data-theme="dark"] override) — not a hardcoded hex.

  2. If it touches a card tile, it goes through cardTileHTML() (or boardCardHTML() for the live battlefield specifically), not a new bespoke template.

  3. If it's a new hover/click flourish, it's driven by real interaction, not a permanent loop — and it's opted into deliberately per-context, not applied globally.

  4. It has its own distinct SoundKit cue if it represents a new mechanic, built from tone()/ noise() only — and that cue/visual is genuinely distinguishable from every other mechanic's, not a reused "close enough" tone or glyph.

  5. If it's a new skill/status VFX event, it needs no special-casing to queue correctly — it just needs a real, distinct ev.type (or a distinct ev.kind if it's shaped as statusFx) so vfxKindOf() buckets it apart from every other mechanic; verify the same-kind-vs-different-kind 200ms/500ms breathing rule reads right in a real multi-effect round, not just in isolation. And check it isn't SILENT: a new statusFx kind with no matching branch in renderVfxForEvent produces no error of any kind, just nothing — cross-reference the engine's events.push({type:'statusFx', kind:...}) call sites against the front end's if/else chain rather than trusting a visual skim (this is exactly how bleed and esprit went unnoticed for a while — see context-vfx-animation.md's "Skills/VFX/SFX coverage audit" section).

  6. Any new dropdown is alphabetized (except placeholders and Rarity).

  7. It was checked at a real mobile viewport width, not just desktop.
  8. It was checked in both light and dark.

  9. If it reveals a genuine platform limitation, that limitation is disclosed honestly rather than faked or silently dropped.

  10. New card art follows section 9: natural anatomy, the right genre for the card's power, and distinct from its siblings on at least two of pose / equipment / scene / background.

  11. Its labels lean on context: no word that the control's position already makes obvious (section 6, "Think contextually"), with the full meaning kept in aria-label.

claude/mechanics-guideline.md read before: a new mechanic, skill or status

Bramblewood Arena — Mechanics Guide (mandatory before shipping any new mechanic)

How this doc is used

Read this before designing or implementing ANY new card effect, status, resource, trigger, action, or combat rule — and before touching an existing one. It is a checklist of the shapes and conventions already established, so a new mechanic slots into the existing system instead of becoming a one-off exception. Where a design question is flagged below as "ask, don't guess," that's not a suggestion — build the same way this project already treats these: pose the concrete question(s) to the user and wait, rather than picking an interpretation and building it. The context-combat-engine.md and context-economy-progression.md docs are the per-system deep reference this doc summarizes into cross-cutting rules — read the relevant one too for exact function names and current edge cases.

1. Resource model — two systems, never conflate them

In-match resources (Gold/pl.acorns, Prayer, Devilry, Stone, Lumber, Elemental Energy) exist only during a live match, reset every game, gate card costs, and are shown in the in-match HUD. Out-of-match currencies (Gold, Gems, Magic Dust, Metal) persist in localStorage, power card leveling and Conquest rewards, and only ever appear on the Player/Forge/Conquest tabs. Both systems currently use the word "Gold" for different things — a known, flagged overlap, not a bug to silently fix by renaming one of them. Do not rename or merge either currency without checking roadmap-and-backlog.md's "Rename Gold → Stone" item first — it's deliberately not started because it needs a design answer (what would Lumber/Elemental Energy each be FOR) before it's a build, not a guess. The out-of-match Gold currency renders with coinIconHTML() (a custom SVG), never the 🪙 emoji, which is reserved for the in-match resource — keep that visual distinction; it's the one thing currently telling the two Golds apart at a glance.

Stone is a tier-2/advanced resource (locked in 2026-09-21) — do not author ordinary card costs or requirements against it. Every unit now grants a flat 1 Lumber on discard (Structure vs. non-Structure no longer matters, see game-design-v32-addendum.md's economy note), and refine (the Elemental Energy converter) consumes Lumber, not Stone, to match (2026-09-19 fix). Lumber is the standard, broadly-available resource a normal card should cost or require. Stone stays in the data model but is dormant by default — nothing grants it via discard/pitch, and the only way to gain any right now is the gainStone custom-trigger action (see ACTION_DEFS) — intentionally, so it's available for a future advanced/gated mechanic without being something every deck accumulates incidentally. When designing a NEW card (including the upcoming first real card batch), a resource-gated cost or a gainStone/consumes-Stone ability should be the deliberate exception for something meant to feel rare/late-game-ish, never the default choice a common or early-curve unit reaches for — reach for Lumber (or Gold/Prayer/Devilry, per their own existing roles) instead. 2. Skill/passive architecture

Every passive lives in PASSIVE_DEFS (or, for the handful with richer parameter shapes, directly in SKILL_DEFS) with a key, label, kind, and a desc() function. Four kinds cover everything so far — use the matching one rather than inventing a new shape:

  • number — a plain stacking or scaling magnitude (Poison, Armor, Rally).
  • boolean — an on/off passive with no parameter (Guardian, Stealth, Rage).

  • twoNumber — a paired value, most often chance+duration (Freeze, Sleep, Paralyze, Blind, Shock) or time+damage (Explode).

  • selectNumber — a dropdown that picks a mode, which may itself reveal a companion number field depending on the choice (Chained's break-condition picker is the reference example). This is the general-purpose row kind for "pick a mode, and only some modes need a number" — reuse it rather than hand-rolling a new conditional-field UI.

When a mechanic needs its own extensible list of options (Chained's break conditions today, something similar tomorrow), follow the CHAIN_BREAK_OPTIONS() pattern: one small function returning an array of {value,label}, with a comment marking it as "the one place to add more" — don't inline a growing list of conditions directly into the skill definition.

Resistance and Weakness deliberately live OUTSIDE the "+ Add Skill" list, in their own dedicated add/remove pill UI on the card form — they're common enough, and paired enough (a Resist and a matching Weakness net to 1x automatically), to earn their own area rather than crowding the generic skill picker. A future mechanic with a similarly-paired, similarly-universal shape is a candidate for the same treatment; most new mechanics are not, and belong in the normal list.

Audit correction (2026-09-29): the pairing above describes the intended design, but no card in canonical/cards.json has ever actually been authored with a weakness — 18 cards carry resist, zero carry weakness. Treat Weakness as designed-but-unauthored, not as an existing paired system with real examples, until a card actually uses it.

Prefer the generic Custom Triggers system (TRIGGER_DEFS/ACTION_DEFS, an effects.triggers entry) over a new dedicated hardcoded field whenever the generic system already covers the same timing and action. (2026-09-21, "Make consistent the abilities" pass — Arrow N/Arrow(=Attack) were migrated off effects.missile onto the generic system on 2026-09-20, and On Attacked: Spawn off effects.onAttackedSpawn on 2026-09-21, both onto a plain On-Trigger + "Spawn card(s)"/"Deal damage" trigger row.) A dedicated field is still the right call when the generic action genuinely can't reproduce the needed behavior — e.g. effects.onDeathSpawn was deliberately KEPT as its own field rather than migrated, because it has real placement timing (refill the exact slot the dying card vacated, deferred until after the round's whole death-filter pass) that the generic spawnCard action's plain "append to a flank" doesn't replicate. Check whether the timing/placement actually matches before defaulting to "migrate it" — when it does match, prefer the generic system; when it doesn't, keep the dedicated field and say why in a comment, the same way this file does.

Audit check (2026-09-29): verified directly against the live canonical/cards.json (334 cards) — effects.missile and effects.onAttackedSpawn both return zero hits. This migration is genuinely complete, confirming the claim above. (A first audit pass flagged this as incomplete, but that pass was run against a stale 238-card project-doc mirror rather than the live 334-card file the game actually builds from — corrected here after re-checking against the real source.)

3. Status-effect shapes

Four shapes are already established — pick the one matching a new status's real behavior instead of inventing a fifth:

  1. Stacking numeric, ticks or decays every round — Poison (ticks as damage), Bleed (ticks on the card's own actions), Corrode (decays 1/round, saps effective Attack). Use this when the effect should compound with repeat application and fade or resolve on its own schedule.

  2. Plain permanent passive — a boolean or number PASSIVE_DEFS entry with no duration at all (Rage, Guardian, Armor, Rally). Use this when the effect is just "always true while this card is on the board," no timer involved.

  3. Chance+duration timed lockout/debuff — Freeze, Sleep, Paralyze, Blind, Shock: each landed attack has a Chance% to apply for Duration round(s), stored as {chance, duration}. Use this for "sometimes happens, wears off after N rounds" effects, and pick a distinct break/interaction rule per status the way these five each do (Sleep breaks on any damage taken; Frozen doesn't; Paralyze re-rolls every round) rather than treating all timed effects as identical once applied.

  4. No-fixed-duration, break-condition lockout — Chained: no timer at all, cleared only by a configurable trigger (maybeBreakChain, extensible via CHAIN_BREAK_OPTIONS). Use this only when the request genuinely describes a condition-based release rather than a countdown — don't default to this shape just because it's the newest one.

4. Trigger & action vocabulary

Triggers and actions are both flat registries (TRIGGER_DEFS, ACTION_DEFS) that the Codex's Reference tab renders directly from — add a new trigger/action to the registry, never hand-write Reference tab text, or the two will drift.

The single most-often-mis-designed distinction: onReady fires exactly ONCE, the round a card's Wait first reaches 0 — not every round after. For "does something every round this card is Ready," use perTurn instead. This has already caused one real bug (Dark Points' "generates N every turn" needing to move off onReady) — when a request says "every turn"/ "every round," reach for perTurn, and when it says "the moment it's ready"/"once ready," reach for onReady; don't assume they're interchangeable.

Other triggers worth remembering precisely: onKill fires for melee kills only, not ranged/ triggered damage; onAttacked fires when a card is hit and SURVIVES; onColumnSpawn fires for either side spawning into that lane, not just an ally. When a new trigger is genuinely needed, add it to TRIGGER_DEFS with a desc precise enough that a future session won't need to re-derive its exact firing rule from the engine source.

Audit correction (2026-09-29): the generic effects.triggers system itself is used by only 13 of 238 cards, and within that small sample the actions used are narrow (mostly gainGold on kill, one-shot buffs). perTurn — this section's own worked example for the Dark Points fix — appears on zero authored cards. Most of this vocabulary is real and working, but largely undemoed in actual content.

5. Combat/column semantics — ask before touching

The board is {left:[], center:[], right:[]} per side; center holds exactly one card and is where the first card played always lands. combatColumnsOf() gives each side's raw column numbering (center=0, left flank negative, right flank positive, counted out from that side's own center) — this is the gathering/bookkeeping structure, but it is not what decides who an attacker actually swings at.

Corrected 2026-09-21 (this section previously described the PRE-V26 strict same-column rule as current, which it no longer is — found while investigating why test_column_align.js was failing about half the time; see game-design-v26-addendum.md for the full history). Actual live targeting goes through resolveLiveTarget(), the rank-interlock/parity facing rule: each side's WHOLE row (left+center+right, left-to-right) is treated as one centered rank. An attacker at position i of an n_S-card rank faces position jf = i + (n_E-n_S)/2 in the enemy's n_E-card rank. Matching parity (n_E-n_S even) → jf is a whole slot → exactly one direct opponent (or the castle, if that slot is empty/out of range) — this is the common case and reads like the old strict rule whenever both sides' live counts happen to share parity. Mismatched parity → jf lands between two enemy slots → the attacker interlocks with both: a 50/50 pick each swing (or 50/50 vs. the castle if only one of the two candidate slots is real, or the castle outright if neither is). Because every attacker resolves its own facing independently on its own turn, a card straddled by two interlocking enemies can genuinely be hit by both of them in the same round, not just one shared coin flip. opposingCardOf() is a separate, deterministic (non-random) variant of the same math for "who's directly opposite me" triggers (Render, Explode, Gash) — it always tries the lower/floor candidate first, falling back to the upper one, never rolling a coin, so those triggers stay predictable even on an interlocked board. Guardian adjacency, Thorns, and Sweep/Swipe's flank-continuation all key off combatColumnsOf's raw numbering directly (adjacency and "next card down the flank" are still well-defined there); only the primary attack TARGET goes through the interlock resolution above.

Two related questions remain standing "ask, don't guess" items — do not build either without the user's explicit answer first, because guessing wrong means a real rebuild, not a tweak: field "rebalancing" to recenter an uneven flank spread (moving cards between flank arrays, not just renumbering columns), and the Evade/Evasion merge (two genuinely different dodge maths, not two names for one mechanic). If a new request touches this same flank/column territory, treat it with the same caution — pose the concrete behavior-determining question(s) rather than picking an interpretation. (A third question — "does a card facing two opponents get attacked once or twice" — used to be listed here too; it's answered above, by the interlock rule's own mechanics, not a separate open decision.)

Audit note (2026-09-29): the Evade/Evasion split isn't just a theoretical fork to resolve before it matters — it's already live in 13 cards under two different shapes: effects.evade (a number, 1 or 2) on 7 cards (Plains Zebra, Arctic Fox Raider, Mountain Goat Climber, Taiga Lynx, Snowshoe Hare, Mangrove Kingfisher, Frost Hare Sprinter) vs. effects.evasion (a boolean) on a different 6 (Acacia Giraffe, Blind Cave Fish, Shimmerwing Stag, Reef Manta Glider, Cuttlefish Illusionist, Camouflage Frog). Resolving this only requires updating ~13 cards today; it gets more expensive to unwind the longer both shapes keep getting authored onto new cards.

6. Card data & leveling

canonical/cards.json is the only hand-edited source of card data — bulk roster changes happen there and get rebuilt, never as bulk live-db seed docs (the db has a 5,000-document cap, and the baseline is never re-seeded into it). A card's level (0-10 today) is independent of its rarity and splashEffect fields — leveling shows as a small badge, never changes the rarity band. The stat curve (1 + 0.06L + 0.004L², floored at base+level) is a known choke point (getCardDefs()) — any UI showing a card's live attack/health should read through it (or the board's own live instance) rather than the raw baseline, or a leveled card's boost silently won't show. The AI currently shares your per-defId level table (a known, flagged gap, not a secret bug to quietly patch without telling the user) — don't build around an assumption that leveling is already owner-scoped.

Audit note (2026-09-29, checked against the live 334-card canonical/cards.json): rarity is populated on 65 of 334 cards (19.5%) — 32 common, 30 starter, 3 rare — the other 269 (80.5%) have no rarity value at all, and nothing above rare has ever been assigned (no Epic/ Legendary/Ancient exists in the actual data despite the full ladder being documented elsewhere). Anything that reads rarity today (deck-limit rules, drop tables, rarity-tinted UI) is working off a field that's 4/5 empty. Treat rarity as a system with only its bottom two rungs authored, not a finished ladder in active use.

There is exactly ONE combat engine implementation (bramblewood-engine.js), shared by the live Play tab and the Simulator's Web Worker — never fork combat logic between the two contexts, even for a performance shortcut. getCardDefs() (baseline merged with the live-db overlay, minus tombstones) is the one correct read path for card data everywhere in the UI. 8. Process & decision discipline

  • Flag a mid-sentence cutoff rather than guess at how it finishes. The project's own history (see the Bramblewood — Open Items microsite, https://claude.ai/artifact/LwqZ67zLJNhnwBQ29dJmXE, and the version addenda) has multiple standing examples — follow the same pattern: quote what was actually said, note where it cut off, and ask, rather than completing the thought yourself.

  • When a request is genuinely ambiguous on a system with real rebuild cost if you guess wrong, ask 1-3 concrete, numbered questions rather than building your best interpretation — the Heroic-tier leveling-curve questions and the combat-column questions above are the reference examples of the right granularity (specific enough that a one-line answer unblocks the build).

  • Every shipped mechanic gets its own new Playwright test file, driving the real engine function (matchState.engine.makeBoardCard, a real resolveRound()/placeCard() call) rather than only asserting on hand-constructed state — and a full regression re-run (batched, per section 7) before calling anything delivered.

  • Update the relevant context-*.md doc in place once a change ships — edit the section that describes current behavior, don't just append a changelog line; the changelog belongs in the version addendum, not the context doc.

Before you ship a new mechanic, verify:

  1. It uses one of the four established PASSIVE_DEFS/SKILL_DEFS kinds, or one of the four established status-effect shapes — and if neither fits, that's a signal to double-check the request rather than freelancing a fifth shape.

  2. Any new trigger/action is registered in TRIGGER_DEFS/ACTION_DEFS, not hand-added to the Reference tab separately.

  3. If it touches column/flank targeting at all, it either respects the existing rank-interlock facing rule (section 5) or the user has explicitly answered the specific behavior question first — don't assume the old strict same-column rule still applies.

  4. It has a dedicated new engine-level test using real engine calls, plus a clean full regression re-run.

  5. It has a SoundKit cue and a renderVfxForEvent branch (see style-guideline.md section 3-4) — for a new statusFx sub-kind specifically, cross-reference the engine's events.push({type:'statusFx', kind:...}) call sites against renderVfxForEvent's statusFx if/else chain (see context-vfx-animation.md's "Skills/VFX/SFX coverage audit" section) rather than trusting a visual skim — a missing branch fails completely silently, no console error.

  6. The relevant context-*.md doc has been updated in place to describe the new current state.

  7. It doesn't gate a normal card's cost/ability on Stone — see section 1's tier-2 resource rule; use Lumber (or Gold/Prayer/Devilry per their existing roles) unless the card is deliberately meant to be a rare/advanced exception.

claude/context-combat-engine.md read before: combat rules and the engine

Context: Combat Engine

Read this before touching combat resolution, targeting, turn order, or any card effect/trigger. Update it in place (not as a changelog) when the rules described here change. Full mechanic-by- mechanic history lives in game-design.md; this is the current-state reference.

Board model

Each player's row is {left:[], center:[], right:[]}. center holds exactly one card. The first card either player plays in a match always lands in center, regardless of which side (left/right) was requested — subsequent cards go to whichever flank was actually chosen. If a card dies out of center and a flank has cards, the nearest flank card collapses into center automatically (a 50/50 coin flip when both flanks are non-empty) — this is the collapseIn event.

Columns are numbered symmetrically per side, both sides sharing one numbering scheme, with center as column 0. combatColumnsOf() is the one function that derives a card's column from its array position — never infer column position any other way.

Turn order

Attackers are gathered (gatherAttackers: Wait=0, not Reloading/Stunned/Shell-skipped), then sorted by Quick-keyword first, then by absolute board column left-to-right across BOTH sides (sharing one column numbering), falling back to side (enemy before player) only when two attackers share a column. This means play visibly alternates top/bottom as it goes left to right, not "resolve one whole side, then the other." Which side wins a same-column tie alternates by round (not hardcoded to one side).

Targeting

An attacker's primary target uses the rank-interlock/parity facing rule (resolveLiveTarget): both sides' whole rows are centered as one unit and matched by position, so unequal row counts correctly interlock instead of just comparing raw column numbers — a card can end up facing one direct opponent, two straddled opponents (50/50 pick), one opponent-or-castle (50/50), or the castle outright, depending on parity. If there's no live opponent to resolve to, the attack goes straight to the enemy HQ. Stealth overrides targeting entirely and always hits the HQ directly, ignoring column state.

Sweep and Swipe are both "extra hit" keywords that key off the primary target's resolved column, but they are NOT the same mechanic:

  • Sweep (effects.sweep = N, a number) continues further down the SAME flank the attacker is facing, past the primary target, for N additional live cards (findNextLiveCardBeyond). It never touches the castle — if it runs off the end of that flank, the extra hits just don't happen.

  • Swipe (effects.swipe = true, a boolean — redesigned 2026-09-21) hits the two enemy columns immediately flanking the primary target's own column (target.col-1 and target.col+1), regardless of which flank the attacker itself is on. A live card in one of those columns takes a full hit; an empty/off-board flank column redirects that swing straight to the enemy castle instead (no Siege bonus — Siege is reserved for the PRIMARY hit landing on the castle). So a lone defender with nothing on either side of it eats the castle hit twice — once per empty flank. Swipe only fires when the primary attack itself landed on a card (there's no reference column to flank from if the primary hit already resolved straight to HQ).

Both Sweep's continuation hits and Swipe's flank hits get their own independent Evasion roll, Guardian redirect, and full per-hit status treatment (poison/bleed/scar/Chained-break/Sap/kill- credit/onAttacked) — same as a primary hit, just resolved a second (or third) time.

Resolution order (one full round, synchronous in the engine)

Round-start custom triggers → poison ticks (deliberately BEFORE Renewal/Regen/Round-Start/Per- Turn, so a Renewed card still eats one guaranteed tick) → gather attackers → sort (Quick, then column, side breaks ties) → normal attacks (Stealth override; primary hit always connects; Guardian may redirect; Sweep/Swipe extra hits are each independently Evasion-gated; thorns reflection; onAttackedSpawn; Shell/Expose/poison queued) → death cleanup (bounty gold, onDeathSpawn, exile-on-death, onKill triggers) → end-of-round upkeep (Shell activate/deactivate, Reload cooldown, Stun clears, Wait decrements once, onReadyDamage/missile(onReady)/render(onReady) fire, onReadyGold/onReadyPrayer pay out) → death cleanup again → game-over check.

Important: the engine runs an ENTIRE round synchronously, including removing dead cards, before any of it is animated client-side. The UI replays the event log afterward as a paced sequence. This is why matchState.replayCards (hp/status snapshot) and matchState.replayRows (row-membership snapshot) exist — a card that died mid-round is already spliced out of the live board array by the time its OWN earlier-in-the-round events get replayed, so the UI can't just query the live board for it. Any new per-event UI logic that needs a card's state mid-replay should read from these snapshots, not the live board, unless it's a freshly-spawned uid the snapshot doesn't know about yet (live board is the correct fallback there).

Trigger/effect vocabulary

Triggers: onSpawn, onReady (fires once, the round Wait first hits 0 — not every round), onDeath, onAttack, onAttacked, onKill (melee kills only, not ranged/onReadyDamage), onExile, onAllySpawn, onRoundStart. Actions: damage, gain gold/prayer, draw, spawn, buff/ debuff attack or health, poison, expose, stun, reduce-wait-of-spawned-ally, exile self. The Codex's Reference tab is generated from the same registry the editor's dropdowns use, so it can't drift from what's actually implemented.

Passive keywords currently implemented: Armor, Thorns, Swipe, Sweep, Rage, Expose, Guardian, Quick, Reload, Shell, Stealth, Evasion/Evade, Bleed, Fester, Rupture, Rally, Esprit, Bloodlust, Berserker, Regenerate, Chained, Resist, Weakness, Scurry, and more — see game-design.md's per-version sections for what each does; this doc doesn't re-derive every one since the Codex Reference tab is the always-current source of truth for their exact current behavior.

Known open design questions (do not guess at these — ask first)

  • Column facing when flank counts mismatch (a lane with more cards on one side than the other) — largely addressed by the rank-interlock/parity facing rule (resolveLiveTarget), but see game-design-action-items.md, Category: Combat rules for any remaining edge cases.

  • Field "rebalancing" to recenter an uneven flank spread — a bigger change than it sounds, since several mechanics (Guardian adjacency, Thorns, sweep-continuation) lean on today's flank-array semantics. See the same doc.

  • Evade/Evasion merge — two genuinely different dodge maths (alternating vs. probabilistic), not just two names for one mechanic. Needs a decision on which semantics survive.

Context: Economy & Progression

Read this before touching costs, rewards, currencies, or the leveling/Forge system. Update it in place (not as a changelog) when any of this changes.

Two separate currency systems — do not conflate them

In-match resources (exist only during a live match, reset every game): Gold (pl.acorns field name — a historical artifact, not a typo), Prayer, Devilry, and Stone (added later as a fourth). These gate playing cards (cost, prayerCost, devilryCost, exile costs) and are generated by onSpawnGold/onReadyGold/onSpawnPrayer/onReadyPrayer effects, bounty kills, and discarding a hand card for gold (max once per turn, human only). Shown in the in-match HUD.

Out-of-match currencies (persist across matches, localStorage-backed via loadCurrencies()/saveCurrencies()): Gold, Gems, Magic Dust. These power card leveling (below) and only ever appear on the Player/Forge tabs, never inside a live match's HUD. Naming overlap is a known, flagged issue — both systems currently use the word "Gold" for different things. The in-match resource's rename to "Stone" was proposed specifically to resolve this but is a separate, not-yet-done backlog item (see roadmap-and-backlog.md) — don't assume it's done, and don't casually rename either currency without checking that backlog item first, since a rename touches dozens of call sites (see that doc's own note on why it's not a quick tweak).

Devilry ("Dark Points") generation shapes

Devilry (pl.devilry) is an in-match resource with several ways to generate it, all landing on the same field via the same ensureStat(...).devilryGenerated bookkeeping and pushing the same {type:'devilry', ...} replay event — a new generation shape should follow this pattern rather than inventing a parallel one. As of 2026-09-21, the full set:

  • effects.onSpawnDevilry / effects.onReadyDevilry — legacy hand-authored top-level fields (mirroring Gold/Prayer's own onSpawnGold/onReadyGold shape). onReadyDevilry is a "per round while Ready" payout (gated on c.wait===0, in the same board-wide pass that also grants onReadyGold/onReadyPrayer), not a one-time "just became ready" trigger — same onReady-vs-perTurn naming trap mechanics-guideline.md already calls out for other onReady*-named hooks.

  • effects.triggers with {on:'perTurn', do:'gainDevilry', amount:N} — the generic Custom Trigger route, now the intended way to AUTHOR a new "generates Devilry every ready round" card from scratch (see test_dark_points.js and its own comment on why perTurn was corrected from an earlier, wrong onReady authoring).

  • effects.inherentDarkness (number, added 2026-09-21) — a named PASSIVE_DEFS/SKILL_DEFS convenience preset for exactly the onReadyDevilry payout above (same gate, same bookkeeping, same event shape) — lets a card carry "generates N Dark Points per round" as a plain numeric "+ Add Skill" row instead of hand-authoring the Custom Trigger. Implemented as its own if block right next to onReadyDevilry's in bramblewood-engine.js (additive if a card somehow has both, though no card is expected to).

  • The archetype-wide Devilry-line discard bonus (discardCardByUid() in arena_app.js, darkPointBonus) — any card whose inferMechanicLine(...)==='devilry' grants +1 Devilry when PITCHED (discarded for its resource yield), on top of its normal pitch yield. This is an archetype-level rule, not a per-card effect field.

  • effects.coreEvil (boolean, added 2026-09-21) — a CARD-level pitch-time bonus, +1 Devilry the moment this specific card is pitched, independent of the Devilry mechanic line entirely (a card with no Devilry archetype tag at all can still carry it) and additive with the archetype-wide bonus above if a card happens to have both (implemented as coreEvilBonus computed alongside darkPointBonus in discardCardByUid(), summed into one darkPointBonus total).

Both new passives also extend the ★ Dark-Point abadge condition (arena_app.js, the e.onSpawnDevilry||e.onReadyDevilry||... check) — any future Devilry-generation shape should be added to that same condition, or a card carrying it will show no ★ badge at all despite genuinely granting Dark Points.

Card leveling (0→10)

Every card has an independent level 0-10, stored in myCardLevels (localStorage-backed via loadCardLevels()/saveCardLevels()), keyed by defId. Leveling up costs Magic Dust + a smaller amount of Gold, rising per level. The stat curve is 1 + 0.06L + 0.004L² (exactly +100% at level 10), floored at base + level so a low-stat card's early levels are never rounded away to nothing by the multiplier. Leveling does NOT change a card's rarity band or visual rarity treatment — it's shown as a small level badge instead, deliberately kept independent of the rarity system.

getCardDefs() is the one choke point that applies leveling to a card's live stats — anywhere in the UI that reads a card's attack/health for display should go through it (or the board's own live instance data, for a card actually in play) rather than reading CARD_DEFS_BASELINE directly, or a leveled card's boost won't show up.

Known open limitation: stats are looked up per-defId in one shared table — a leveled card's boost is NOT yet scoped away from an AI opponent who happens to field the same card. This means today, leveling YOUR Otter Centurion also makes the AI's Otter Centurion stronger if it draws one. Flagged, not silently worked around — needs a per-owner stat-scoping pass before this is fully correct.

Board row overflow + cross-card stacking (2026-09-21)

.board-row uses overflow-y:clip; overflow-clip-margin:90px;, not overflow-y:hidden. Per explicit report ("Elements are still being cut out - in the battlefield"): the row pairs overflow-x:auto (needed for the horizontal-scroll-instead-of-wrap behavior, see the "visual 'cards forming a 2nd row' bug" entry in game-design-action-items.md) with a vertical overflow rule. Per the CSS Overflow spec, pairing overflow-x:auto with overflow-y:visible silently PROMOTES the visible axis to auto too (risking an unwanted vertical scrollbar) — so overflow-y can't just be set to visible to stop clipping normal in-play decoration (damage floats, status badges, the FIGHT sign, hover-zoom) that legitimately pokes past the row's box. overflow-y:clip sidesteps the promotion (it's not visible, so it doesn't trigger the pairing rule) while overflow-clip-margin:90px gives 90px of breathing room before anything actually gets clipped. This is the same fix shape already used once before for .speech-bubble (see that class's own CSS comment) — if a similar "element getting cut off" report comes in for a DIFFERENT scrollable container, check for this same overflow-x:auto + overflow-y:hidden pairing before assuming it's a z-index problem.

Cards do NOT get a permanent per-card z-index. The instinct for "cards should have higher layer order" is to just add z-index:1 (or similar) to the base .board-card rule — don't. Any non-auto z-index on a position:relative+ element creates a NEW, ISOLATING CSS stacking context for that element's descendants, which traps a card's own .dmg-float inside that one card's local stacking order — it can then no longer out-rank a NEIGHBORING card's badges/other elements, exactly backwards from the actual request ("the numbers should have the highest" layer order, across the whole row, not just within their own card). Resting cards are left at z-index:auto (no isolating context at all) specifically so .dmg-float's own z-index:40 (see below) can reach across sibling cards freely. A card that's actively lunging into its attack gets a temporary, animation-scoped lift instead: animateAttacker() adds .is-attacking (z-index:8) right when the lunge starts and removes it in every completion path (both GSAP timeline onComplete branches and the non-GSAP fallback's final setTimeout) — narrow enough in scope and duration that it never creates a lasting isolating context, and 8 still sits comfortably below .dmg-float's 40. Current cross-card z stack, low to high: resting .board-card (auto) < .abadge/skill badges (3) < hover-zoom (5) < .is-attacking (8) < .dmg-float (40). If a new element needs to sit in this stack, place it deliberately in this ladder rather than picking an arbitrary number.

Context: VFX & Animation

Read this before adding or changing any animation, particle effect, or entrance/exit behavior. Update it in place (not as a changelog) when the system changes. This code is described in the source itself as "extremely carefully-tuned... with many bugfix comments warning against structural changes" — treat that warning as real; prefer additive changes over restructuring.

The entrance/Flip system (GSAP)

renderBoard()'s newEls handling drives every card's entrance. Two paths exist: a GSAP path (used when GSAP is available, which is always in the shipped build) and a no-GSAP fallback (kept for robustness, not actively used). Flip.from() handles the "existing cards slide to their new position" reflow; new cards are explicitly excluded from what Flip touches and animated on a separate timeline instead — this split exists because Flip's onEnter/onLeave callbacks don't reliably fire for brand-new elements in this GSAP build, and because Flip was once found silently re-diffing against stale, already-discarded DOM elements when new-card detection wasn't kept separate (see game-design-action-items.md, "Landing impact" entry, for the full bug history — don't reintroduce that coupling).

pendingEntranceOrigins (a Map<uid, {x, y, rotate}>) is how a new card's entrance tween starts from a REAL on-screen point (where it came from) instead of a generic fall-from-above. Consumed once (deleted on use) so it can never leak onto a later, unrelated card reusing the same uid space. Three producers as of 2026-09-18:

  • Played from hand: set in playCardByUid, using the hand tile's own live bounding rect, keyed by the HAND uid (this one specifically survives into the board card, since placeCard preserves the hand-card's uid rather than reassigning — this is the ONE case where hand-uid == board-uid; every other producer below keys by the board card's own uid, which is often different from any hand uid involved).

  • onAttackedSpawn (e.g. Bee Drone spawning on being hit): set from the attacked card's own live position (ev.nearUid).

  • onDeathSpawn (e.g. Rot-Swollen-Carcass spawning 3 Maggot Swarmlings on death): set via lastDeathOrigin, a one-shot heuristic — the death-event handler records the dying card's on-screen center right before removal; the very next onDeathSpawn spawn event (which always immediately follows its triggering death within one round's replay) consumes it. Added 2026-09-18, task list item 2.

When an origin IS found, the entrance starts at scale:.16 (tuned down from an earlier .5) so it reads as "popping out of the spawner" rather than "a small card flying in." When no origin is recorded, the generic fall-in (scale:.4, y:-52) is used instead.

Trap to remember (a real bug hit while building item 2): a played card's HAND uid is not always the same as its final BOARD uid — placeCard()'s return doesn't reassign the hand-uid in every path, but any code that needs the definitive board uid (e.g. to anchor a speech bubble or VFX to the just-played card) should read it from the 'play' event's own uid field (events.find(ev=>ev.type==='play').uid), not the uid the play action was originally called with. pendingEntranceOrigins' hand-play producer is a documented, deliberate exception where the hand uid does carry through — don't assume that generalizes elsewhere.

renderVfxForEvent(ev)

The central dispatcher — one big function with an if(ev.type==='...') branch per engine event type (hit, hitHQ, death, spawn, heal, poisonTick, statusFx, etc.). Each branch typically: sound cue → floating text/number → element-specific animation (shake, lunge, flash). New event types should follow this same pattern rather than introducing a parallel dispatch mechanism.

Skills/VFX/SFX coverage audit (2026-09-21)

The reliable way to check "does every mechanic actually have a sound and a visual" is to cross-reference the two ground-truth lists against each other, rather than eyeballing renderVfxForEvent's if/else chain in isolation:

  • every events.push({type:'statusFx', kind:...}) call site in bramblewood-engine.js (the full set of kinds the engine can ever actually emit), against

  • every else if(ev.kind==='...') branch inside renderVfxForEvent's ev.type==='statusFx' block (the full set of kinds the front end actually handles).

Doing this the first time turned up two kinds the engine had been pushing for a while with no matching branch at all — bleed (the "Bleed opposite" custom-trigger action) and esprit (the Esprit passive's on-ally-spawn self-buff) — both fired completely silently: no sound, no float, no status refresh, the exact same class of gap as the pre-existing Scurry/ bleedTick silences found in earlier audit passes (see game-design-action-items.md). Both are now wired up:

  • kind:'bleed' → SoundKit.bleedApply() (a distinct apply tone, separate from bleedTick()'s round-tick sound, mirroring Poison's own apply-vs-tick split) + a '+N🩸' float using the new .dmg-float.bleed CSS class (arena_template.html — was missing; floats were silently falling back to the base --attack red) + an rc.bleed mirror into the replay snapshot so the mid-round status badge stays in sync.

  • kind:'esprit' → SoundKit.espritTone() (a warm ascending triangle chime, deliberately gentler than Berserk's growl or Momentum's escalating notes, since Esprit is a camaraderie effect, not a rage/kill-streak one) + a '🤝 +N⚔' float on the card that just grew — same "self-buff floats on the attacker's own tile" pattern Berserk/Momentum already use, no rc mutation needed for the same reason those two don't need one (the permanent Attack gain shows up via the normal stat display at round end).

Covered by test_bleed_esprit_statusfx.js. When adding a new custom-trigger action or passive that can push a statusFx event (or any new event type at all), run this same cross-reference before calling it done — a new kind/type with no branch fails silently, with no console error to catch it, so it's easy to ship an invisible mechanic by accident. This check is now folded into mechanics-guideline.md's and style-guideline.md's "before you ship" checklists.

Coverage audit, follow-up pass — Crit/Rend/Fester/Rupture/Frenzy (2026-09-21)

Same cross-reference method, next five keywords off the ~30-keyword list. Findings:

  • Crit had no dedicated sound/flourish at all — landing a crit doubled damage completely silently (only a small 💥 tucked into the battle-log text). Now: SoundKit.critTone() + a 💥 Crit! float via keywordCuesForHit, suppressed when ev.ambush is also true (Ambush gets its own distinct flourish and shouldn't double up with Crit's on the same hit).

  • Rend (bypasses Armor) and Fester/Rupture (bonus damage = the attacker's own poison/bleed stacks) folded silently into the plain hit-damage number, zero attribution — pixel-identical to an ordinary hit for the same final total. The engine now reports these as pure DISPLAY flags on the hit/hitHQ event (rend, festerBonus, ruptureBonus — the underlying damage math is unchanged, these only tell the VFX layer WHY the number is what it is): computeHitDamage/damageCard compute rendBypass = rend && nominalArmor>0 (only flags true when Rend actually mattered — a Rend attacker vs. an unarmored target reports rend:false, since nothing was bypassed); festerBonus/ruptureBonus are captured as named locals right where the bonus is added to atkThisRound. keywordCuesForHit reads these off the event and floats 🗡 Rend — Armor bypassed! (+SoundKit.rendTone()) / attributed +N☠/+N🩸 floats (+SoundKit.festerBite()/ruptureBite()) alongside the normal damage number. logText's 'hit' case appends matching text annotations.

  • Frenzy's bonus-attack requeue pushed no event at all — the second swing replayed as an indistinguishable ordinary hit, nothing signaling why a card acted twice. Skill/status VFX queuing (2026-09-21)

Skill and status VFX are never simultaneous — the replay loops in resolveRound() play one event at a time, await sleep(delayForEvent(ev, prevKind)) between each, so an effect always finishes before the next one starts. delayForEvent() picks the gap based on whether the CURRENT event is the same "kind" as the one immediately before it (tracked as lastVfxKind/lastWaitVfxKind in the two replay loops, computed via vfxKindOf(ev)):

  • Combat beats keep their own fixed, dedicated pacing regardless of neighboring kind: hit/ hitHQ/evaded (900ms, or 1260ms if ev.ranged), death (550ms), render (780ms).

  • Every other event type (the "skill/status VFX" bucket — poisonTick, bleedTick, statusFx and its many sub-kinds, heal, sap, explode, namedBuff, collapseIn, spawn, revive, waitTick/ready, ...) gets 200ms if vfxKindOf(ev) matches the previous event's kind, or 500ms if it doesn't (including the very first event in a sequence, which has no previous kind to match). This is the "bubbly, obvious, distinct" pacing rule — see style-guideline.md's "Skill VFX" section for the full design rationale; this doc is just the implementation pointer.

  • vfxKindOf(ev) returns ev.type for everything except statusFx, where it returns 'statusFx:'+ev.kind — statusFx bundles many visually/audibly distinct sub-mechanics (poison/freeze/stun/scar/blind/shock/corrode/berserk/momentum/bleed/esprit/...) under one event type, so two different ev.kinds must never be treated as "the same kind of thing" for queuing purposes.

  • Both places that replay an event log — the main combat/skill event loop and the separate Wait-timer/"next turn" replay — track their own lastVfxKind local variable and pass it into delayForEvent(); a new replay loop added later should follow the same pattern rather than calling delayForEvent(ev) with no previous-kind context (which always falls back to the 500ms "different kind" gap, safe but overly conservative for a genuinely repeating effect).

  • All of the above is still scaled by matchState.speedMult exactly like every other event delay always was (1x/1.5x/2x/3x, floored at 18ms).

claude/context-audio.md read before: sound

Context: Audio

Read this before touching any sound, any volume control, the settings menu, or the speech framework's voice cues. Update it in place (not as a changelog) when any of this changes.

System overview

All sound is synthesized in-browser via the Web Audio API — no external audio files, no CDN dependency, consistent with the single-file-artifact constraint. Everything lives in one IIFE, SoundKit, near the top of arena_app.js.

Two primitives everything else is built from:

  • tone(freq, dur, type, gainPeak, delay, volOverride) — a single oscillator envelope.
  • noise(dur, gainPeak) — a short filtered noise burst (explosions, impacts).

Every named cue (SoundKit.hit(), SoundKit.death(), SoundKit.gold(), ~40 more) is one or a few calls to these two primitives with different frequency/duration/type combinations. Adding a new cue means adding a new named method that calls tone/noise — never bypass them, since volume gating (below) only happens at that one choke point.

Volume model (three independent sliders)

As of 2026-09-18 (task list item 7), there are three persisted volume values, each 0..1:

  • sfxVolume (default 1, bw_sfxVolume in localStorage) — gates tone()/noise() directly. This is what almost every existing cue in SoundKit responds to.

  • voiceVolume (default 0.8, bw_voiceVolume) — gates only SoundKit.voiceTone(), the speech framework's "voice blip" (see below). Kept separate from sfxVolume deliberately, so a player can mute combat SFX but keep character chatter audible, or vice versa.

  • musicVolume (default 0.6, bw_musicVolume) — persisted, but there is no music system yet. No oscillator or audio element reads this value today. It exists so a future music track has a real, already-chosen volume to start at instead of defaulting to full blast the day one ships. The settings panel's Music slider carries a small note in the UI saying so — do not remove that note without actually wiring up music.

Exposed API (all on the SoundKit object): getSfxVolume()/setSfxVolume(v), getVoiceVolume()/setVoiceVolume(v), getMusicVolume()/setMusicVolume(v). Each setter clamps to [0,1] and persists to its own localStorage key. setSfxVolume(0) also calls stopAll() so dragging the slider to zero mid-cue cuts off immediately rather than just blocking the next one.

Back-compat only: isMuted()/setMuted(v) still exist (isMuted() ⇔ sfxVolume<=0), kept in case something outside this codebase still calls them. Nothing in this app calls them anymore — the settings panel talks to get/setSfxVolume directly. Don't build new features against isMuted/setMuted.

The settings panel

HTML lives in arena_template.html (.settings-wrap / #settingsBtn / #settingsPanel, replacing the old single mute-toggle button). Wiring is initSettingsPanel() in arena_app.js (search for that name) — a small IIFE that binds each of the three <input type="range"> sliders to its matching getter/setter pair, syncs the displayed percentage, and handles open/close (gear-icon click, outside click, Escape key).

To add a fourth slider later (if a real music system or another audio channel shows up): add the <input type="range"> + label row to the .settings-panel markup, add a {el, val, get, set} entry to the sliders object in initSettingsPanel(), done — the open/close/sync plumbing is generic and doesn't need touching.

Speech framework's voice cue

SoundKit.voiceTone(seed) is a two-tone blip gated by voiceVolume (not sfxVolume), added specifically for the speech/dialogue framework (task list item 8). It takes a numeric seed — callers pass the speaking card's own uid — and derives a small pitch offset from it (340 + (seed%7)*55), so the same physical card instance sounds consistent across its own lifetime without any real voice recording or per-character audio assets. This is a deliberate placeholder for "a character's voice, represented by an sfx from a set list" — see context-vfx-animation.md's speech-bubble section for the visual half, and game-design-v30-addendum.md for why this shipped as a scaffold rather than a full content pass (real per-character personality needs the user's creative input, not just engineering).

tone() takes an optional final volOverride parameter specifically so voiceTone() can reuse the exact same oscillator-envelope code while gating off voiceVolume instead of sfxVolume — if a future audio channel needs the same treatment (a fourth independently-gated cue family), follow this same pattern rather than duplicating the oscillator logic.

Known gaps / open items

  • No actual music track or music-playing code exists — musicVolume is inert. Building this would need either a synthesized ambient loop (consistent with the no-external-files approach) or embedding a short audio file as a data: URI (size-budget tradeoff to weigh).

  • The speech framework's line content is generic placeholder chatter (see context-vfx-animation.md and game-design-v30-addendum.md) — no per-character voice identity beyond the deterministic pitch-by-uid trick.

  • voiceTone's pitch derivation is a simple modulo, not tuned for actually sounding distinct per character — worth revisiting if/when real character personalities get designed.

Genre prompt prefixes (see style guide §9 for when to use which)

  • ANAT (always appended for animals): natural animal anatomy, not anthropomorphic, no hands, never standing upright like a human,
  • Cute: Cute Pokemon-style pixel art creature portrait, big sparkling expressive eyes, soft round chubby shapes, bright cheerful palette, clean dark outlines, + ANAT
  • Brave: Pokemon-style pixel art creature portrait, confident determined eyes, sturdy rounded shapes, rich warm palette, dynamic action pose, clean dark outlines, + ANAT
  • Menacing: Pokemon-style pixel art portrait of a fearsome creature, sharp narrowed glowing eyes, angular silhouette, dramatic low-angle lighting, deep saturated shadowy palette, imposing pose, clean dark outlines, + ANAT (dragons: "natural dragon anatomy with four legs and two wings, not humanoid"; golems/trolls/elementals: no ANAT)

Then: <subject + pose>, <equipment>, <scene>, <background>. Rule of thumb by stats: Attack ≤2 and Health ≤10 → Cute; Attack ≥6 or Health ≥24 → Menacing; otherwise Brave.
