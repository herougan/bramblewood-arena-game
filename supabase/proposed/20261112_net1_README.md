# NET1 proposed SQL (2026-11-12)

File: `20261112_net1_scale.sql`. Status: **not applied**, waits for the owner's "apply it". Plan: `docs/network-scale-plan-2026-11-12.md`.

What it does (no rows change, so no backup table is needed):

1. **Five indexes** for reads every open tab repeats: the card_overrides change poll (`updated_at`), the raid bars (`raid_week_attempts (cycle, fought_at, id)`), friendships by requester, live matches by player. `profiles(last_seen_at)` is left out on purpose: the heartbeat writes that column, and an index would make every heartbeat write an index too.
2. **RLS that scales.** The 20 policies the performance advisor flags call `auth.uid()` once per row; they now use `(select auth.uid())`, which runs once per query. Same rules and roles. Three duplicate SELECT policies are dropped (each is covered by another policy on the same table with the same or a wider condition), and `reward_rules`' admin ALL policy becomes insert / update / delete.
3. **`card_overrides.updated_at` always moves.** A trigger sets `now()` when an UPDATE leaves `updated_at` unchanged (a hand-run fix). The game's change poll and the new per-device copy of the overrides (NET1) rely on `updated_at`.
4. **Advisor tidy.** `progress_score` gets a fixed `search_path`; `guard_progress_shrink()` (a trigger function) can no longer be called through the API.

The client works the same before and after: nothing in `arena_app.js` depends on this file.

After applying: run the read-back queries at the end of the file, then the performance and security advisors.
