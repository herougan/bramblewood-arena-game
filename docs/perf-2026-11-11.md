# Performance: fight effects lag (2026-11-11, package PERF2)

**The report (owner, 00:06):** "even on my macbook, the game lags alot - playing effects. How do we optimise this?"

## Short version

The effects themselves were not the problem. Every effect adds small elements to the page (sparks, puffs, numbers, emoji pictures), and three things made each addition expensive:

1. **Three CSS rules made Chrome restyle about 500 elements (half the page) on every DOM change of a fight.** Rewritten, same look.
2. **Five CSS rules aimed at the card name made every name on the page restyle at each change.** Rewritten, same look.
3. **GSAP's first move of each spark cost two style passes and a layout, one spark after another.** Every effect module now skips that probe, and the big particle loops prepare their sparks as one batch.

Result on the same seeded fight: the page's main-thread work during a fight is down by about 60%, and the heavy-effects run by about 75%. Style work, the biggest cost, is down by about 85-90%. Nothing on screen looks different (checked with computed styles, old build against new).

## How it was measured

`node tests/perf2-2026-11-11.js --bench` (build first). It uses the real game page in headless Chromium at 1366x768, with Effects set to High and Auto-lower off. Math.random and the match seed are fixed, so every run plays the same fight. Two phases:

- **Fight**: Map mw, fight 5-3, with Auto-play on for your side, so it is CPU against CPU. Three rounds: plays, attacks, poison, field ticks, deaths and the round banners (37 effect events).
- **Effects**: a fixed run of heavy effects, one second apart, on the board that the fight leaves. Dragon arrival, meteor, tornado sweep, lightning, swarm, poison cloud, avalanche sweep, fireball, supreme arrival, earthquake, tsunami sweep and regenerate.

It records frame times (requestAnimationFrame), long tasks, elements added per effect, and a Chrome trace of the main thread. The trace gives CPU time for style, layout and paint, the number of style passes and the elements restyled. It runs at 1x and with the CPU slowed 4x.

**About the frame numbers:** the test machine is a shared 2-core box, and other agents' balance runs and tests kept its load average at 12-31 during these runs. Under that load the browser gets a small share of a core. Frame times and long tasks then mostly measure the other jobs, for both builds. The **main-thread CPU time** in the trace is thread time, so the load affects it much less: it is the number to compare. On your MacBook, frame times follow the CPU numbers much more closely.

## What was wrong

### 1. Three rules restyled half the page on every change (CSS)

`:has()` rules make Chrome re-check styles under an element when something inside it changes. Chrome only re-checks the elements the rule could select. If the rule's target is a bare `*`, a `:not(...)` or similar, it gives up and restyles the whole subtree. Body, the rows and every card tile have `:has()` rules on them, so each spark, damage number or emoji picture added during a fight restyled about 500 elements. In the trace, styles took 4.4 s of the fight's 7.1 s of main-thread CPU, with 236,000 elements restyled in three rounds.

- `.board-row:has(> :nth-child(21)) > * + *`: now `> :where(.board-card) + :where(.board-card)`. A row only holds board cards, and `:where()` keeps the old specificity.
- `.winloss-card:has(.rw-panel) .winloss-stats > :not(.rw-panel)`: removed. The grid it was part of is already switched off by `.winloss-card:has(.rw-panel) .winloss-stats{display:block !important}`, so it did nothing visible.
- `.conquest-layout[class*="map-theme-"] *`: a `[class*=]` test left of `*` had the same effect for every class change on any element. Now `.conquest-layout.conquest-layout *`, with the same specificity and the same elements.

### 2. A :has() aimed at the card name restyled every name (CSS)

Five rules selected `.nm` through a `:has()` on the card or the row. Every DOM change then restyled every card name on the page. The scroll's SVG backgrounds make a name one of the costlier elements to restyle.

- `.card-tile:has(.badges ...) .nm`: now `.card-tile > .nm:has(~ .badges ...)`. The badges always come after the name.
- `.card-tile:has(> .waitbadge[data-wait-total]) > .nm` and the two `.card-tile:has(.waitbadge) .badges-bottom.status-chips` rules: now sibling rules (`.waitbadge ~ ...`), with no `:has()`. The wait clock is the tile's first child.
- ENG26 (names hidden in a row of 9+ units on small tiles): the row marks itself (`--eng26-many:1`, a `:has()` on the row). The name reads the mark through a container style query inside the existing size query.

`node tests/perf2-2026-11-11.js --equiv old.html` builds fixtures for every rewritten rule and compares computed styles in the old build and this one. All 14 are identical, including ENG26 (9 small tiles: hidden; 8: shown; 9 big: shown).

### 3. GSAP's first move of each spark (JS)

The first time GSAP moves an element, it reads the element's transform. Sometimes it also runs a check meant for elements hidden with `display:none`: it sets `display:block` and measures again. It does this when the element has no offsetParent and no transform yet. Every `position:fixed` effect overlay has no offsetParent. So each new spark cost two forced style passes and a layout, one spark after another. A 17-piece poison cloud forced 34 style passes in one frame.

- Each effect module's overlay helper (SkillFX, FX.A-G, procfx, the EN* helper `en2Layer`) now marks its fixed overlays as shown, which skips that check. An overlay is never `display:none`.
- SkillFX's 42 particle loops (bursts, embers, swarm, regenerate, poison cloud, thorns, flakes, stars and so on) now build their overlays as one batch with `layers()`. GSAP reads the whole batch in one style pass before anything moves, instead of one pass per spark.
- FX.C reads its overlays once before its timeline plays, and FX.B reads its overlays and particles once before it builds. FX.D's poison flurry builds all its bubbles first, then reads them in one pass.
- The board's pip centring (`vis3CentrePips`, run on every board redraw) used to alternate reading and writing for each pip. Now it reads every pip first, then writes them.

**Starting one effect**: the main-thread time of the call, plus the style and layout pass it forces. Median of 7, two runs, with the browser given a larger CPU share (`nice -15`):

## What I did not change, and why

- **The snap guard** (`boardSnapGuard`): it reads every board card's position each frame for 2.5 s after a redraw, about 0.2-0.5 s of a three-round fight. It mostly pays for the frame's own style pass early, and it fixes a real "cards teleport" bug, so I left it alone.
- **The name scroll's SVG backgrounds**: each `.nm` paints several data-URI SVGs. Chrome re-lays out those SVG documents for each size it draws, which shows as thousands of "SVG changed" layout invalidations. Changing them to a PNG strip would be cheaper but is an art change.
- **Card filter flashes** (poison's sickly tint, bleed, thorns): a short CSS filter tween on the card tile repaints the tile for about a second. Changing it to an overlay would change the look slightly.
- **The dragon's arrival**: a 1.5 s battlefield-sized `mix-blend-mode: multiply` darkening, plus a blurred emoji shadow growing to 2.6x. It is rare and short; a normal-blend overlay would look a little different.
- **Lazily started tweens**: tweens on elements that GSAP had not read before still read them when they start, in the middle of a frame. These are now cheap (no probe, no page-wide restyle), but each is still one style pass.
- **`:has()` rules on html, body and .content-wrap**: removing all five cut a single spark's insertion cost by a further 2-3x in isolation, but only about 10% of style time in the fight. Replacing them needs class toggles in `syncPageFlags` and `switchTab`, outside this package.
- **Effects settings**: Settings already has Effects High / Medium / Low / None, and Auto-lower effects (on by default). Auto-lower drops one level, once per session, when the frame time averages over 33 ms for 2 s. No new setting was added.

## Options for the owner

- Auto-lower effects could step down twice (High to Low) instead of once when a fight stays slow. Today it stops at Medium.
- The name scroll's SVG backgrounds could become a PNG strip: cheaper to paint on every card, an art change.
- Card filter flashes and the dragon's multiply layer could become plain overlays: cheaper, with a slightly different look.

## Guardrails added

`tests/perf2-2026-11-11.js` runs with every `node tests/run.js`. It needs no browser and takes under a second. It fails if:

- a `:has()` or `[class*=]` rule gets a featureless target again;
- a `:has()` rule targets the card name again;
- an overlay helper loses the shown mark;
- a SkillFX particle loop of 5 or more builds its overlays one at a time;
- the pip centring interleaves reads and writes again.

The same rule for new code: keep `:has()` rules aimed at a class, and create a batch of sparks before moving any of them.
